## 2. Fix state hub 404s (P0)

**This is the clearest real production bug. No redesign. Make the existing feature reliable.**

Sitemap and internal links already point at `/parks/state/utah`, `/parks/state/california`, etc. Production can 404 because the page fetches **all parks** and then `notFound()` if the filtered list is empty — including when the API fails.

**Bug site:** `next-frontend/src/app/parks/state/[stateCode]/page.jsx`

Current shape:

- `STATE_MAP` already knows valid states.
- `getParksForState()` calls `GET ${BASE_URL}/parks?all=true` (all ~474 parks), then filters client-side.
- On fetch failure it returns `[]`.
- Page then does `if (parks.length === 0) notFound()`.

So an API timeout, empty payload, or backend blip becomes a **404 for a real state**.

**Fix:**

- Stop fetching all parks just to render one state.
- Use a state-specific query or a stable local state mapping.
- Call `notFound()` only for an actually invalid state (not in `STATE_MAP`).
- API failure must not become a 404. Render an error/empty-with-retry state, or serve cached/stale parks.

Linked from: `sitemap.ts`, Discover states, park detail state hubs (`lib/parkSeo.js`, `lib/seoBrowseHub.js`).

## 3. Standardize analytics events (P0)

Dashboard and code must agree on what each event means. Renaming everything is optional; unused/mismatched names are not.

**Current mismatch (examples):**

| Enum / dashboard expects | What actually fires |
|---|---|
| `user_signup` | unused / dashboard still aggregates it |
| signup in product | `auth_signup_success` (Vercel) / other paths |
| `user_login` | unused |
| login in product | `auth_login_success` |
| `conversation_create` | never fires |
| `ai_chat` | fires without reliable user identity |

**Canonical model to move toward** (keep existing names if cheaper, but map them in one place):

- `page_view`
- `park_view`
- `signup_success`
- `login_success`
- `trailie_session_start`
- `trailie_message`
- `trip_created`
- `trip_shared`
- `pdf_export`
- `voice_session_start`
- `compare_view`
- `map_view`
- `crowd_calendar_view`
- `where_next_pick` (Where Next already uses `user_action` metadata actions — keep that contract unless analytics work explicitly migrates it)

**Code to reconcile:**

- Enum: `server/src/models/Analytics.js`
- Retention list: `server/src/config/analyticsRetention.js`
- Client: `next-frontend/src/utils/analytics.js`
- Admin aggregations: `server/src/controllers/analyticsController.js` (still queries `user_signup`)
- Tests: `next-frontend/src/utils/__tests__/analytics.test.js`

One mapping table (code + dashboard) is the deliverable. Do not invent a second analytics system.

## 4. Attach identity/context to every event (P0)

Every event should carry what is available:

- `sessionId`
- anonymous/browser ID
- `userId` when logged in
- path
- source/referrer
- park code where relevant
- CTA ID where relevant
- timestamp

**Problem this fixes:** cannot reliably tell anonymous users from logged-in users.

Schema already has `userId`, `sessionId`, `referrer`, `pageUrl`. The gap is population, not empty columns. Client `trackBackend` in `analytics.js` must send identity; server `hoistAnalyticsFields` / `normalizeClientEvent` must persist it; `ai_chat` must not be an exception.

Do not put raw Where Next free-text destinations into analytics payloads (existing Where Next rule R19).

## 6. Keep historical aggregates (P0)

Raw Analytics TTL is **30 days** (`ANALYTICS_RETENTION_DAYS` in `server/src/config/analyticsRetention.js`). `api_call` is **7 days**.

In October we cannot recreate August product behavior from raw events.

Keep raw-event TTL if needed for storage. Add durable **daily and monthly aggregate** records, for example:

**2026-08-27**

- real sessions
- park viewers
- map users
- compare users
- Trailie users
- voice users
- signups
- new TripPlan authors
- crowd calendar users
- Where Next submissions

Then August → September → October is comparable.

## 7. Remove crawler noise (P1)

~40K crawler-shaped `/guides` sessions vs ~5K human-scale product sessions. Dashboard must distinguish **human/product traffic** from **bot/crawler traffic** without manual cleanup each time.

Bot detection/filtering or a classification layer on ingest/aggregate. Prefer classifying at write or rollup time so historical aggregates stay clean.

## 8. Fix only genuine SEO/crawl issues (P1)

Ignore: hashed Next.js chunks, old static files, stale robots entries, intentional redirects.

Focus:

- state 404s (item 2)
- genuine park pages crawled but not indexed (~32 concerns in the audit, not 1,071)
- crawlable parameter variants (`?tab=`, `?from=`) that should not be standalone search URLs

Older GSC work lives in `docs/plans/seo-coverage-fixes-2026-05.md`. Use it as history, not as a mandate to reopen every URL.
