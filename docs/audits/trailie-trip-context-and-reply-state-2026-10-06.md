# Trailie trip context and reply state

Local changes only. No production deployment or paid model requests were used for verification.

## Diagnosis

The reported Glacier request reused the guest's Yellowstone canonical plan and three-day memory. The model-first guard correctly rejected replacement (`existing_plan_requires_patch`, `plan_day_count_mismatch`). A subsequent useful prose response was incorrectly sent as a terminal error. The client then logged that same failure twice.

## Contracts

- Sample/demo, park, compare, intent-guide, new-chat, and personalized entry URLs allocate a new conversation within the existing guest session. Guest identity, quota, and previous histories are preserved.
- `entry=new-trip` is an action, never a resume instruction: any supplied conversation ID is discarded. Once allocated, navigation consumes that action and changes the URL to `entry=continue&conversation=<new ID>`. Repeating the same sample allocates another ID; refreshing the active URL restores it.
- Ordinary messages use the current conversation ID, including “make it 5 days.” Existing canonical mutation guards remain enforced.
- Guest canonical plans, conversation history, planning memory, reloads, resume links, and sign-up migration are scoped by conversation. Quota and pending-turn admission remain shared across the guest identity.
- A rejected mutation followed by usable correction prose completes the conversation with `artifactStatus.status=save_failed`. It does not replace the saved canonical plan. The notice mentions an unchanged saved trip only when a prior plan exists.
- A genuine model failure remains a reply failure. The client logs one diagnostic with response ID, code, and phase.

## Browser fixture investigation

The sentence “Five relaxed days in Glacier. This answer remains visible.” was a deliberately intercepted Playwright response in a separate browser context. It was never generated by GPT or sent to the backend. That context was mistakenly left open, then inspected and closed.

Read-only local MongoDB checks found zero records for conversation IDs `38c13745-ec35-4f66-bb24-9c403f454d30` and `967eda22-1c9c-4ac2-bdfd-98c1a83537cc`, zero records for the fixture guest, and zero records containing that sentence. Normal-browser local storage did not contain the fixture. No fixture text exists in application source.
